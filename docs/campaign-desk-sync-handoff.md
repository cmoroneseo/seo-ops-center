# Campaign Desk — build the forecast sync receiver

Paste this document into your coding agent. You are working in **Campaign Desk**, the agency's weekly forecast tool. You are not working in SEO Ops Center. Do not change SEO Ops Center.

SEO Ops Center searched this repo for `campaign desk`, `campaign_desk`, `forecast`, and `allocation`. There is no Campaign Desk API client, base URL, or credential. The old `monthly_plans` table is an internal SEO Ops stub and is not Campaign Desk. **Campaign Desk needs the three endpoints below.** If you already have equivalents, change them to this contract instead of adding a second one. If these endpoints already match this contract exactly, stop and say that no further Campaign Desk work is required.

SEO Ops will not call you until an owner turns the flag on. There is no cron. A person confirms a preview, then SEO Ops sends one run.

## Auth

Shared secret, server to server. Not an end-user login.

```
Authorization: Bearer <shared secret>
Accept: application/json
Content-Type: application/json
```

SEO Ops stores the secret as `CAMPAIGN_DESK_API_TOKEN` and the origin as `CAMPAIGN_DESK_API_BASE_URL`. Compare the bearer value in constant time. Missing or wrong secret: `401` with `{ "error": "unauthorized" }`. Never log the header or copy it into an error message.

## Endpoints

Base URL has no trailing slash. All paths are under `/v1`.

### 1. List people

`GET /v1/people`

Used to match a teammate by email before any hours are sent. Return every person who can receive a forecast.

```json
{
  "people": [
    { "id": "desk_carlos", "email": "cmorones@marketingempiregroup.com" },
    { "id": "desk_abel", "email": "amiranda@marketingempiregroup.com" }
  ]
}
```

`id` is your stable person id (any non-empty string). `email` is the mailbox you store. SEO Ops trims and lowercases both sides. Two people with the same email are treated as not mapped, so keep emails unique. Do not return secrets.

`200` and that body. Anything else is a failed lookup. SEO Ops will not guess, and it will not mark people "Not mapped" when this call fails.

### 2. Upsert a run

`PUT /v1/forecast-runs/{runId}`

`runId` is a UUID generated by SEO Ops. The same id must not create a second copy.

Behavior:

- New `runId`: store the body. For each `weekStart` in the body, replace **that week's SEO Ops allocations** with this body. Leave other weeks alone. Return `200`.
- Same `runId` and the same body: do nothing. Return `200` with `"idempotent": true`.
- Same `runId` and a different body: do not change stored hours. Return `409` with `{ "error": "idempotency_conflict" }`.
- Body fails the schema below: `422` with `{ "error": "invalid_payload", "message": "<short reason>" }`.

```json
{
  "runId": "11111111-1111-4111-8111-111111111111",
  "status": "accepted",
  "idempotent": false
}
```

A newer run for the same week replaces the older run's allocations for that week. Deleting the older run afterwards must not wipe the newer week.

### 3. Undo a run

`DELETE /v1/forecast-runs/{runId}`

Remove that run's effect.

- If this run is the newest accepted body for a week, restore the previous accepted run that includes that week. If there is no previous run, clear that week's SEO Ops allocations.
- If a newer run has already replaced the week, leave the newer week in place.
- Deleting a run that is already deleted: `200` with `"idempotent": true`.
- Deleting an id you have never seen: `404` with `{ "error": "run_not_found" }`.

```json
{
  "runId": "11111111-1111-4111-8111-111111111111",
  "status": "deleted",
  "idempotent": false
}
```

## Payload

One allocation is one person email, one client (or the internal bucket), one week, and one source. Send hours as a two-decimal **string**. `minutes` is the canonical integer. `hours` must equal `minutes / 60`, rounded half away from zero to two places (`240` → `"4.00"`, `90` → `"1.50"`, `10` → `"0.17"`). Reject a JSON number in `hours`.

`source` is `actual` or `estimate`, and it must match the week's `basis`. SEO Ops uses tracked time for the current week and earlier weeks (`actual`). Later weeks use task estimates (`estimate`). Meetings are `bucket: "internal"` with `clientId: null` and `clientName: "Internal"`, even when the meeting was about a client. Breaks are not in the payload. Unmapped time is not in the payload. Allocation percent is **not** in the payload. Do not invent `0` when a line is absent.

`weekStart` is the Monday of the week, `yyyy-MM-dd`. A run contains 1 to 4 weeks. An empty `allocations` array means that week should be cleared, not that the week is unknown.

```json
{
  "runId": "11111111-1111-4111-8111-111111111111",
  "source": "seo-ops-center",
  "organizationId": "22222222-2222-4222-8222-222222222222",
  "weeks": [
    {
      "weekStart": "2026-10-12",
      "basis": "actual",
      "allocations": [
        {
          "personEmail": "cmorones@marketingempiregroup.com",
          "campaignDeskPersonId": "desk_carlos",
          "clientId": "33333333-3333-4333-8333-333333333333",
          "clientName": "Northwind Plumbing",
          "bucket": "client",
          "source": "actual",
          "minutes": 240,
          "hours": "4.00"
        },
        {
          "personEmail": "cmorones@marketingempiregroup.com",
          "campaignDeskPersonId": "desk_carlos",
          "clientId": null,
          "clientName": "Internal",
          "bucket": "internal",
          "source": "actual",
          "minutes": 60,
          "hours": "1.00"
        }
      ]
    },
    {
      "weekStart": "2026-10-19",
      "basis": "estimate",
      "allocations": [
        {
          "personEmail": "amiranda@marketingempiregroup.com",
          "campaignDeskPersonId": "desk_abel",
          "clientId": "33333333-3333-4333-8333-333333333333",
          "clientName": "Northwind Plumbing",
          "bucket": "client",
          "source": "estimate",
          "minutes": 180,
          "hours": "3.00"
        },
        {
          "personEmail": "amiranda@marketingempiregroup.com",
          "campaignDeskPersonId": "desk_abel",
          "clientId": null,
          "clientName": "Internal",
          "bucket": "internal",
          "source": "estimate",
          "minutes": 60,
          "hours": "1.00"
        }
      ]
    }
  ]
}
```

Field rules:

| Field | Rule |
| --- | --- |
| `runId` | UUID. Same value as the URL. |
| `source` | Exactly `seo-ops-center`. |
| `organizationId` | UUID of the SEO Ops organization. Store it with the run. |
| `personEmail` | Lowercase email. This is the match key. |
| `campaignDeskPersonId` | The `id` you returned from `GET /v1/people`. |
| `bucket` | `client` or `internal`. |
| `clientId` | UUID when `bucket` is `client`. JSON `null` when `internal`. |
| `clientName` | Client name, or exactly `Internal`. |
| `minutes` | Integer `>= 0`. Canonical duration. |
| `hours` | String matching `minutes`. |

## Errors

Respond with JSON `{ "error": "<code>", "message": "<short reason>" }`. `message` is optional except on `422`. Do not include the bearer token, stack traces, or the raw body in `message`.

| HTTP | `error` | When |
| --- | --- | --- |
| 401 | `unauthorized` | Missing or wrong bearer secret. |
| 404 | `run_not_found` | `DELETE` for an id you have never stored. |
| 409 | `idempotency_conflict` | `PUT` for a known `runId` with a different body. |
| 422 | `invalid_payload` | Schema violation. Say which field failed. |
| 500 | `unavailable` | Your server failed. SEO Ops will not mark the run synced. |

## Acceptance tests

Implement these against your endpoint. Use a synthetic organization. Do not write the production Marketing Empire Group organization.

1. `GET /v1/people` without a bearer token returns `401` and `unauthorized`. The body does not contain the secret.
2. `GET /v1/people` with the secret returns Carlos and Abel by those emails. A second call returns the same ids.
3. `PUT` the sample body. A second `PUT` of the same body and same `runId` returns `idempotent: true` and does not double the hours. Carlos's week of 2026-10-12 is 4.00 client hours and 1.00 internal hour, not 8.00 and 2.00.
4. `PUT` the same `runId` with `minutes: 241` and `hours: "4.02"` returns `409` `idempotency_conflict`. The stored week is still 240 minutes.
5. `PUT` a line whose `hours` is the JSON number `4` returns `422`. A line whose `hours` is `"4.01"` while `minutes` is `240` returns `422`.
6. An internal line with a non-null `clientId`, or a client line with a null `clientId`, returns `422`.
7. A new `runId` for week `2026-10-12` with only the internal line replaces that week. The client line from the first run is gone. Week `2026-10-19` from the first run is unchanged.
8. `PUT` a week with `"allocations": []` clears that week. It does not store a fake 0-hour row.
9. `DELETE` of the newest run restores the previous allocations for the weeks that run owned. `DELETE` again returns `idempotent: true`. `DELETE` of a random UUID returns `404` `run_not_found`.
10. `DELETE` of an older run, after a newer run replaced its week, leaves the newer week's hours in place.

## Version 2

Version 1 above stays the payload while `CAMPAIGN_DESK_SYNC_V2` is anything other than the exact string `true`. Version 2 is the body in Campaign Desk `docs/campaign-desk-sync-v2.md` (PR #48). SEO Ops sends it from the same manual Sync to forecast button. There is still no cron. Each new body gets a new `runId`. The same body is reused from `campaign_desk_sync_runs`.

Version 2 rules SEO Ops follows:

- `version` is the number `2`. Unknown keys are not sent. `weekStart` is the Monday. Every item `source` matches the week `basis`.
- `minutes` is an integer from 1 to 1440. `hours` is minutes ÷ 60, half away from zero, two decimal places (`90` → `"1.50"`, `10` → `"0.17"`).
- `itemKey` is stable `kind:id:date`, unique for that person and date.
- The current week and earlier weeks send tracked time, one item per day, per task or event. Later weeks put the task estimate on the task start date. A task with several people splits that estimate evenly. Tracked time stays with the person who logged it.
- Breaks are left out. Out of office is not sent. A client meeting is `kind: "event"` and `bucket: "client"`. An internal event is `bucket: "internal"` and `client: null`.
- People match by email. A client item always includes `name` and `domain` (`domain` is null when SEO Ops has none) plus `campaignDeskClientId` from `campaign_desk_client_links` when a row exists, otherwise from one exact `GET /v1/clients` name match.
- Migration `099_campaign_desk_client_links.sql` creates that map. It is not applied by this change. Apply it before turning version 2 on. Version 1 does not read it.
